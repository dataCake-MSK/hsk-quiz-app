# ADR-0003 클린 아키텍처 4계층과 포트(Repository 인터페이스) 위치

- 상태: 제안
- 날짜: 2026-09-17
- 관련: NB-012, SRS-001, SRS-025

## 맥락
- 로버트 C. 마틴의 클린 아키텍처를 **도메인 / 애플리케이션 / 인터페이스 / 인프라** 이름으로 쓴다. 의존성은 항상 안쪽(도메인)으로만 향한다.
- 기획 메모에는 Repository 인터페이스(추상)를 **인터페이스 계층**에 둔다고 되어 있다. 그런데 유스케이스(애플리케이션)가 그 추상을 쓰면 **안쪽 계층이 바깥 계층에 의존**하게 되어 의존성 규칙이 깨진다.
- 패턴은 처음부터 모두 넣지 않고, 필요해진 시점에 리팩토링으로 도입한다(NB-012).

## 결정
- 폴더(`backend/app/`)
  | 계층 | 폴더 | 들어가는 것 | import 가능 |
  |---|---|---|---|
  | 도메인 | `domain/` | 엔티티(`Word`, `WordStat`, `QuizSession`), 순수 규칙(mastery 계산) | 표준 라이브러리만 |
  | 애플리케이션 | `application/` | 유스케이스, **포트**(`ports/`: Repository·Strategy 인터페이스, `typing.Protocol`) | domain |
  | 인터페이스 | `interface/` | FastAPI 라우터, Pydantic DTO, 응답 변환 | application, domain |
  | 인프라 | `infrastructure/` | SQLAlchemy 모델·세션·Repository 구현, JWT·해싱, 설정, DI 조립 | 모든 계층 |
- **Repository 인터페이스는 `application/ports/`에 둔다**(의존성 역전: 인프라가 애플리케이션의 포트를 구현).
- DI는 FastAPI `Depends()`를 처음부터 사용한다. 프레임워크 기본 방식이라 별도 "패턴 도입"으로 보지 않는다.
- 패턴 도입 시점
  | 패턴 | 도입 시점 | 이슈 |
  |---|---|---|
  | 4계층 폴더 | 스캐폴딩 | SRS-001 |
  | Repository | 유저 소유 데이터(즐겨찾기)가 생겨 user_id 강제·유스케이스 단위 테스트가 필요할 때 | SRS-025 |
  | Strategy | 출제 대상 선택 방식이 2개가 될 때 | SRS-034 |
  | Factory | 문제 유형이 2개가 될 때 | SRS-035 |
  그 전까지는 라우터에서 SQLAlchemy 세션을 직접 써도 된다. 도입할 때 ADR을 새로 쓴다.
- 계층 규칙은 SRS-025부터 테스트로 검사한다(`application`에서 `sqlalchemy`·`fastapi` import 금지).

## 대안
| 대안 | 선택하지 않은 이유 |
|---|---|
| 포트를 인터페이스 계층에 둠(원안) | 애플리케이션 → 인터페이스 의존이 생겨 의존성 규칙 위반 |
| 처음부터 Repository·Strategy·Factory 모두 적용 | 필요 없는 추상화가 먼저 생기고, "왜 필요한지"를 체감하며 배우는 목표와 맞지 않음 |
| 3계층(router/service/repository) | 도메인 규칙과 유스케이스 구분을 배우기 어려움 |

## 결과
- 좋아지는 점: 유스케이스를 DB·프레임워크 없이 테스트, 출제 방식 교체가 쉬움
- 감수하는 점: 초기 파일 수 증가, ORM 모델 ↔ 도메인 엔티티 변환 코드
- 재검토 조건: 계층 간 변환 코드가 기능 코드보다 많아질 때
